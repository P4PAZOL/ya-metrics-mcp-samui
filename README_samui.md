# Форк ya-metrics-mcp для samuiguide.ru

MCP-сервер для Яндекс Метрики, урезанный под задачи гайда по Самуи.
Форк [mrkhachaturov/ya-metrics-mcp](https://github.com/mrkhachaturov/ya-metrics-mcp),
лицензия оригинала (MIT) сохранена. Оригинальные README апстрима — рядом
(`README.md`, `README_ru.md`).

Разбор, почему выбран именно этот сервер из пяти кандидатов —
в `docs/metrika-mcp.md` основного проекта.

## Чем отличается от апстрима

**Набор инструментов сужен с 31 до 7.** Не флагом и не переменной окружения:
регистрации лишних инструментов физически удалены из
`src/ya_metrics_mcp/servers/tools.py`.

Почему не через `ENABLED_TOOLS`, как задумано автором: **эта переменная в
апстриме не работает.** Функция `filter_tools()` написана и покрыта юнит-тестами,
но нигде не вызывается — тулы регистрируются декораторами `@mcp.tool` при
импорте модуля, минуя всякую фильтрацию. Проверено: `grep filter_tools` даёт
только определение, тесты и упоминание в документации автора.

Физическое удаление к тому же надёжнее: опечатка в переменной окружения не
может внезапно открыть агенту все 31 инструмент.

## Оставленные инструменты

| Инструмент | Зачем |
|---|---|
| `list_counters` | Узнать `counter_id` — его требуют все остальные инструменты, а дефолта в конфиге нет |
| `list_goals` | Узнать `goal_id` цели подписки для конверсий |
| `get_traffic_sources_types` | Источники трафика |
| `get_goals_conversion` | Цели и конверсии |
| `get_page_performance` | Посещаемость по страницам гайда |
| `get_regional_data` | География аудитории |
| `get_device_analysis` | Устройства аудитории |

Пять предметных категорий по одному инструменту плюс два инструмента
обнаружения. Без последних остальные неработоспособны: `counter_id`
взять негде.

Набор закреплён тестом `tests/unit/test_enabled_tool_set.py`, который
сравнивает множества целиком. Он падает и когда инструмент пропал, и когда
после merge из upstream вернулся лишний — второе важнее, именно так набор
и расползается обратно. Проверено: возврат `get_drilldown` роняет два теста.

## Read-only

Все семь инструментов помечены тегом `read`, инструментов с тегом `write` в
сервере нет — отдельный тест это проверяет по тегам, а не по именам.
В коде апстрима ноль вызовов `POST`/`PUT`/`DELETE`, только `.get(`.

## Установка

```bash
git clone https://github.com/P4PAZOL/ya-metrics-mcp-samui.git
cd ya-metrics-mcp-samui
python3 -m venv .venv && .venv/bin/pip install -e .
cp .env.example .env      # токен вписать в .env, он в .gitignore
```

Проверка без токена:

```bash
YANDEX_API_KEY=dummy .venv/bin/python -m pytest tests/ -q
```

## Журнал вызовов в панель samui-guide

После каждого вызова инструмента обёртка отправляет `POST` на эндпоинт Django
`/api/metrika/log/`. Панель `/cms/metrika/` в CMS показывает по этим записям,
что агент спрашивал у Метрики — без похода в интерфейс Метрики и без чтения
логов.

### Два разных секрета — не путать

| Переменная | Что открывает | Цена компрометации |
|---|---|---|
| `YANDEX_API_KEY` | Токен Метрики | Вся статистика сайта |
| `METRIKA_LOG_SECRET` | Запись в журнал samui-guide | Мусор в журнале |

**Это разные секреты с разным назначением.** Переиспользовать один вместо
другого нельзя: токен Метрики в теле запроса к журналу не передаётся никогда,
а эндпоинт вдобавок отвергает параметры с именами, похожими на секреты.

### Настройка

```
METRIKA_LOG_ENDPOINT_URL=https://samuiguide.ru/api/metrika/log/
METRIKA_LOG_SECRET=<секрет из прод-.env проекта samui-guide>
METRIKA_LOG_TIMEOUT=3.0        # необязательно
```

Не задан URL или секрет — логирование молча выключено. Локальная разработка
не должна требовать поднятого Django.

### Что отправляется

Только факт вызова: имя инструмента, переданные агентом параметры, успех или
ошибка, длительность.

**Содержимое ответов Метрики не отправляется** — ни целиком, ни фрагментами.
В `result_summary` уходит лишь объём ответа («ответ получен: 1842 символов»).
Журнал отвечает на вопрос «что агент спрашивал», а не «что ему ответили»:
статистика сайта остаётся в одном месте, и копий у неё не появляется.

В параметрах отсеиваются ключи, похожие на секреты, и не отправляются
значения по умолчанию — в журнале видно ровно то, что запросил агент.

### Диагностика: почему панель пуста

```bash
.venv/bin/python probe_log_endpoint.py
```

Зонд читает те же переменные из `.env`, что и сервер, и различает режимы
отказа, **не создавая записи в боевом журнале** — он намеренно шлёт нагрузку
без обязательного поля `status`.

| Ответ | Что значит |
|---|---|
| **400** | Связь и секрет в порядке. Искать надо, дошёл ли вызов до обёртки |
| 401 | Секрет разошёлся с прод-`.env` samui-guide |
| 503 | На проде не задан секрет либо gunicorn не перезапускали |
| 429 | Лимит частоты |
| сеть/таймаут | Эндпоинт недоступен с этой машины |
| «ВЫКЛЮЧЕНО» | Не заполнена одна из двух переменных в `.env` |

Код возврата 0 — путь до журнала исправен, 1 — нет. Значения секретов зонд
не печатает, только их длину.

### Логирование не может помешать инструменту

Три свойства, закреплённые тестами:

- **Отказ логирования не ломает вызов.** Сеть недоступна, таймаут, эндпоинт
  ответил 400/401/429/500/503 — инструмент всё равно возвращает результат
  агенту, а ошибка уходит в stderr MCP-сервера.
- **Логирование не подвешивает ответ.** Таймаут 3 секунды по умолчанию.
- **Предохранитель.** После трёх неудач подряд отправка выключается до
  перезапуска процесса — иначе при лежащем Django каждый вызов инструмента
  оплачивал бы таймаут заново.

Ошибка самого инструмента логируется и пробрасывается дальше как есть: агент
должен увидеть настоящую ошибку Метрики, а не наш пересказ.

## Выпуск токена — чеклист

**Не выполнять до отдельного решения.** Это финальный шаг перед боевым
включением; до него сервер работает и тестируется без реальных секретов.

### Шаг 0. Завести отдельный аккаунт Яндекса

Не использовать основной аккаунт владельца счётчика. Смысл: токен, выданный
гостевому аккаунту с правом только на просмотр, **физически не сможет**
изменить настройки счётчика или удалить цель — независимо от того, что
окажется в коде сервера после очередного merge из upstream. Это сильнее
любой проверки в коде и любого теста.

### Шаг 1. Выдать гостю доступ к счётчику

Метрика → счётчик samuiguide.ru → **Настройки** → вкладка **Доступ** →
добавить пользователя → уровень **«Только просмотр»**.

Не «Полный доступ» и не «Редактирование».

### Шаг 2. Зарегистрировать приложение

Под **гостевым** аккаунтом открыть <https://oauth.yandex.ru/client/new>:

- название: `samui-guide-metrika-mcp`;
- почта для связи: обязательное поле;
- платформа: **Веб-сервисы**;
- Redirect URI: `https://oauth.yandex.ru/verification_code`;
- доступ к данным: набрать в поиске `metrika` и выбрать **только**
  `metrika:read`.

`metrika:write` и `metrika:expenses` **не отмечать**. Форма Яндекса
подписывает права своими словами, не всегда совпадающими с кодом скоупа, —
сверяться нужно по коду под названием, а не по подписи.

### Шаг 3. Получить токен

Скопировать ClientID и открыть, подставив его:

```
https://oauth.yandex.ru/authorize?response_type=token&client_id=ВАШ_CLIENT_ID
```

На экране подтверждения **прочитать список прав** — это то, что реально
получит токен. Токен действует 6 месяцев.

Если Яндекс вернёт прежний токен вместо нового (так бывает, когда токен для
этого приложения уже выдавался), нужно сначала отозвать доступ приложения на
<https://id.yandex.ru/security/apps>, иначе новые права не применятся.

### Шаг 4. Подключить

Токен вписать в `.env` этого репозитория и/или в `.mcp.json` проекта
samui-guide. Оба файла в `.gitignore`; права на файл — `600`.

### Шаг 5. Проверить

Первым вызовом делать `list_counters`: он дешёвый и сразу покажет, видит ли
токен счётчик. Пустой список означает, что гостевой доступ из шага 1 не
выдан или выдан другому аккаунту.

Затем `list_goals` — найти `goal_id` цели подписки, он понадобится для
`get_goals_conversion`.

## Обновление из upstream

```bash
git fetch upstream && git merge upstream/main
```

После merge **обязательно** прогнать тесты: если апстрим вернёт вырезанные
инструменты, гейт упадёт. Не «чинить» его ослаблением проверки — вырезать
инструмент заново и обновить `EXPECTED_TOOLS`.

## Что ещё не сделано

Логирование вызовов в `MetrikaQueryLog` (панель `/cms/metrika/` в CMS
проекта). MCP-сервер работает на машине владельца, а таблица живёт в
прод-базе, наружу не открытой, поэтому писать напрямую он не может —
потребуется HTTP-эндпоинт в Django и обёртка здесь. Разбор вариантов —
в `docs/metrika-mcp.md` основного проекта.
